# Architecture

nx2android turns a player's own Switch game files into a data pack the phone app runs. The player picks the game's file, clicks **Port**, and gets the pack; the app runs the game from it, with no per-game app of its own. Every game the tool supports is a **game profile**; everything all games share is the **core**.

```
gui/  (PySide6 desktop app)
  │  runs `python -m porter port … --progress json`, draws the JSON events
  ▼
porter/  (headless port pipeline, also a CLI)
  │  inputs → extract → rewrite → shaders → host → data pack   (the legacy --game-apk adds the apk stage)
  │  reuses nxnative/scripts/build_ipa_from_nsp.py's steps (imported, not copied)
  ▼
nxnative/  (our fork of seedds/nxnative + the Android port)
  ├─ dm/host, dm/gfx, dm/tools        core: Horizon host, NVN layer, rewriter, shader split   (shared with iOS)
  ├─ dm/android                       core: Android runtime (Vulkan backend, front end, build.py, mkapk.py)
  └─ dm/games/<title ID>/             profiles: game.tsv + shader tables (+ patches.py) + android.tsv
```

## Layers and their rules

| Layer | Where | Holds | Must not hold |
|---|---|---|---|
| **Core, shared** | `nxnative/dm/{host,gfx,tools,third_party}` | What every game and both platforms need. Android differences behind `DM_ANDROID` / `__APPLE__` / `DM_TARGET`. | Game-specific branches. |
| **Core, Android runtime** | `nxnative/dm/android/` | Vulkan replay backend (`gfx_vk_*`), the player front end (`front_player.c`; upstream's APK front, `front_android.c`, is not built here): the machine parts only — the window, the lifecycle, the hold, the physical controller, the settings, the gamepad's layout, the save manager's export and import, the haptics, shaking the device as shaking the controller, the audio, the performance hints; the app draws the gamepad and every panel, the host draws none), the NDK build (`build.py`), the APK writer (`apk/mkapk.py`), the Vulkan shader bundle (`tools/shader_vk.py`), the profile's Android header (`tools/android_profile.py`), the gamepad's layouts (`overlay_default.tsv`: tablet and phone) and its themes (`themes/`: a sprite pack per design, and `themes.tsv`, the table of which game wears which; `themes/README.md`). | Code that depends on a game: no title IDs, game names or per-game branches in code (comments may name the game a rule was found with, as upstream's do). A game that needs something different gets a profile key. |
| **Game profile** | `nxnative/dm/games/<title ID>/` | Data only: `game.tsv` (upstream keys), shader tables, `patches.py` (per-build rewriter cuts), and `android.tsv` (Android keys, below). | Code paths. |
| **Port pipeline** | `porter/` | The stages that turn game files into the data pack; the toolchain check; the profile registry. Runs headless. | UI. |
| **GUI** | `gui/` | Screens over `porter`: setup check, game file, profile status, options, progress. | Pipeline logic: everything it does, the CLI does too. |
| **Distribution** | `packaging/` | The player's bundle (`build_bundle.py`, PyInstaller): one executable that is the GUI and the Python the pipeline runs the engine's tools with (`nx2android.py`), the committed `nxnative/` beside it, the install guide (`INSTALL.md`). | Pipeline logic or toolchains. |
| **Dev tools** | `devtools/` | Scripts for bringing up a game on a connected device (pushing files, screen recording, soak tests, pass traces). The device comes from `devtools/device.json` or `NX2A_DEVICE`. | Anything the port needs. |

The game profile is compiled into the host (`game_profile.h` and `android_profile.h`, generated by `build.py`), as upstream does: porting a game builds its host with the player's NDK, which takes seconds.

The Vulkan pipeline cache is a writable driver product under `DM_ROOT`, separate
from portable shader assets. Its envelope validates renderer ABI, device/driver
identity, length and digest before driver creation. Legacy raw files retain the
Vulkan version-one vendor/device/UUID check and migrate at the next save. Saves
serialize through one I/O lock and fixed temporary name, publish atomically, and
skip identical content by digest; incomplete snapshots and publication failures
remain retryable. The legacy path cannot provide integrity guarantees absent from
the old format.

Immutable Vulkan driver segments share submission scratch only when both their
hash and exact content match in the current epoch. Equality reads a CPU snapshot
of the live c0/c2 prefix (0x648/0x968 bytes), avoiding reads from mapped GPU memory.
A cross-bank hash collision compares the longer prefix, including the shorter
bank's implicit zeros. The 1,024 CPU snapshots cost about 2.35 MiB of content;
GPU-written segments must not enter this cache. This is a correctness guarantee,
not a measured device performance result.

Vulkan pools that cannot use zero-copy keep a CPU snapshot of their synchronized GPU buffer. At completion only bytes changed by the GPU against that snapshot are merged back, preserving independent CPU writes made after synchronization, including writes in the same page. Mapped results are read through a 4 KB CPU buffer before byte comparisons, avoiding repeated byte reads from GPU-mapped memory. The existing cached/uncached pool coverage rules stay in place; a device-to-host memory barrier precedes completion. After a full completion merge, the next incremental sync refreshes only the snapshot blocks it uploads; initialization and untracked pools retain full snapshots. NVN CPU_UNCACHED pools merge only their tracked GPU-write ranges and keep the baseline complete after every merge, as they trusted those ranges before the baseline: an untracked GPU write stays in the GPU copy until a later tracked range over it merges it. A full snapshot at the next sync instead would copy the whole pool before every submission (Unicorn Overlord's 860 MB CPU_UNCACHED pool). The snapshot costs one extra byte of RAM per copied-pool byte and is freed with the pool; zero-copy pools need no snapshot. Games still have to synchronize CPU and GPU writes to the same bytes.

Copied pools can opt into host-cached memory with `DM_VK_POOL_CACHED=1` (off by default). A cached allocation is published only after allocation, mapping and binding succeed; failed attempts release their resources and fall back to the existing host-coherent path (device loss remains fatal). Non-coherent pools flush once per uploaded pool before any submission part is sent: initialization covers the whole mapping, while incremental uploads flush the interval from the first changed block to the last, rounded outward to `nonCoherentAtomSize`. Clean gaps between changed blocks may remain in that interval. A range that reaches the pool tail uses `VK_WHOLE_SIZE` from its aligned start to avoid exceeding the allocation. After the GPU-to-host barrier and completion wait, they invalidate before merging results. With eligible range readback, each pool invalidates one atom-aligned interval spanning its clipped GPU-write ranges, or skips invalidation if none intersect. Other submissions invalidate the whole mapping. Each pool owns and maps its whole allocation; a tail range uses `VK_WHOLE_SIZE` from its aligned offset. Cache-maintenance failure stops the host rather than continuing with stale data. Zero-copy pools and other buffer allocations retain their existing paths.

`DM_VK_POOL_READBACK_RANGES=1` independently opts cached guest pools into range-limited completion merges for submissions containing only known transfer writes and read-only shader descriptors. Writable/unknown shader descriptors (checked before descriptor memo returns), transform feedback and texture-to-guest-buffer writes disable the mode for the whole submission. Uncertain submissions keep full cached-pool merging and whole-mapping invalidation. Eligible ranges keep the baseline complete for both cached and NVN CPU_UNCACHED guest pools because all device writes are covered. Outside the covered writes the GPU copy and baseline stay unchanged; their next tracked sync overwrites whole dirty blocks from guest memory before refreshing those baseline blocks. Uncertain CPU_UNCACHED submissions merge their tracked ranges, as with the switch off, and initialization/untracked pools still copy whole. Both switches are off by default. New GPU buffer-write paths must either register their full destination or force the conservative fallback.

Vulkan indirect compute dispatches copy their three GPU-written group counts into submission scratch memory in command order. A shader that reads c0 gets a private driver segment, outside the immutable segment cache, with the counts at `c0 + 0x200`; the dispatch reads that same record. Without c0, only a 12-byte record is allocated. Argument records may cross chunks of the same pool, with each chunk's buffer offset preserved. All words are validated before any argument copy, and a transfer barrier makes the record visible to both uniform reads and indirect dispatch. Scratch storage is retained until the submission completes. Direct compute dispatches and other driver segments retain their existing content caching.

## Game profiles on Android

A profile is offered for Android when it has an `android.tsv`; the profiles without one (52 of the 54 today, upstream's iOS games) show as "ios only": an experimental port can still try them. `android.tsv` holds, one `key<TAB>value` row each:

| Key | Meaning |
|---|---|
| `status` | `playable` (tested end to end on a device), `wip` (plays on a device, but parts are missing: README.md's Games table says which), `boots` (starts, not playable yet) or `experimental` |
| `tested` | `<version> <device>`: the version and device the status was checked on |
| `package` | The app's package name (default `org.nx2a.t<title ID in lowercase>`) |
| `orientation` | `landscape` (default) or `any` |
| `requires` | Device features the game needs, checked by the installer (the legacy path): `bcn` (BC texture compression) |
| `sysdata` | System data titles the game reads from the console's firmware, 16-digit hex title IDs (`0100000000000802`: MiiModel, the Mii heads Mario Kart 8 Deluxe builds): the port extracts each from the player's firmware dump (`--firmware`) into the data pack's `sysdata/<title ID>/`, and the host mounts it (`DM_SYSDATA`, `dm/host/hle_fs.c`) in place of its stand-in. Never shipped with the tool |
| `setting` | `<name>=<value>`: the host's defaults on first launch (`rumble`, `docked`, `fps`: the frame rate counter in the top left corner, off by default), written to the data pack's `settings.txt`, where the host also keeps the player's own gamepad layout from the app's layout editor (`ui=` rows) and its Snap to grid (`grid`, off by default). The gamepad's own two values (shown, opacity) are the app's preferences now, not the host's: the host keeps them as runtime state (`dm_pad_prefs`) and never writes them |
| `env` | `<KEY>=<VALUE>`: a host switch the game needs on Android, written to the data pack's `env.txt` |
| `overlay` | `<tablet\|phone> <control> <x> <y>`: moves one on-screen control of that layout (`dm/android/overlay_default.tsv`) to x, y as fractions of the window, compiled into `android_profile.h` |

Per-build knowledge stays where upstream keeps it: the rewriter's cuts in `patches.py` / `dm/tools/sdk_patches.py`, keyed by build ID.

## The port

`python -m porter port <game file> -k <prod.keys>` (the phone app's **Port** action) runs these stages. The slow ones (extraction, rewrite, shader split, the translator build, the Vulkan shaders) keep their output with a key of their inputs and are skipped on the next run when the key is unchanged; the host build is incremental (`build.py`), and the data pack is made again each time. The pack records `player_api_revision`, the manual APK/player interface revision from `porter/revision.py`. Gradle generates the Android constant from the same file. Increment it only for incompatible APK/runtime interface changes; ordinary engine fixes, game patches, shaders, APK versions and payload changes do not invalidate installed games. A missing or different revision offers **Update runtime** first. Completed packs run without source files or a build workspace.

`python -m porter rebuild-runtime <pack>` compiles the current player runtime using the final `profile/<titleId>/game.tsv` and `android.tsv` saved during the original port. It does not read keys or source games, or regenerate mods, shaders or RomFS. Compiler switches follow the current APK policy. A fresh runtime and its managed hooks are staged in a new `.runtime-*` directory; an atomic manifest replacement activates the complete set. Failed or interrupted attempts leave the previous manifest and game data intact. Launch copies are refreshed even when file sizes are unchanged. Runtime updates have their own modal state and foreground service. They never enter the port progress screen, port history or source-file bookkeeping. The dialog closes on success; failures offer retry, a full re-port or close. An interrupted process restores a retry prompt from a single pending-pack marker.

Legacy packs without saved profiles cannot use this path and receive a clear suggestion to port again. Compilation failure offers retry or a full re-port; load failures and identifiable native crashes also suggest a full re-port without claiming that old data caused the error. Full re-port still requires source game files and keys, so keeping a backup is useful. Saves, user settings and selected drivers are retained during runtime updates.


| Stage | What | Output (in `<game folder>/<title ID>_build/`) |
|---|---|---|
| inputs | Find the base game, updates and DLC (NSP / XCI / NSZ / XCZ) next to the file that was picked, match the profile, pick the version; check the game folder's drive has room (about twice the picked game's files, the other games in the folder not counted, NSZ / XCZ counted decompressed and once more for their NSP, less an earlier port's build folder; the app's mode asks for once: its pack holds no RomFS, it points at the build folder's own) | |
| decompress | Only with NSZ / XCZ files that a stage below will read (a reused extraction reads none): each becomes an NSP (an XCZ: an NSP of its secure partition), its NCZs expanded and encrypted again with the keys their section tables carry, every NCA checked against its SHA-256 name (`porter/dumps.py`). Deleted once the DLC are extracted, or when the port fails | `tmp/dumps/` (temporary) |
| extract | `nx_extract` (built with the .NET SDK) | `extract/<version>/{ExeFS,RomFS}`, `aoc/` |
| system data | Only for a profile with `sysdata` and a `--firmware` folder (the player's own system content files, `.nca`): `nx_extract --sysdata` writes each title's RomFS; without the folder the port says so in red and the host's stand-in is used | `sysdata/<title ID>/` |
| 60 fps | Only with `--fps60` (below): the profile's own cap, or the build's FPSLocker-Warehouse config converted for the host | `android/fpslock/{fpslock.tsv,patches.py,<build ID>.yaml}` |
| rewrite | `patch_nso.py` with `DM_TARGET=android` | `android/patched_<version>/` |
| shaders | `shader_split.py` (the DLC's own shaders too, `aoc/` given as `DM_SPLIT_AOC`), then `shader_vk.py` (SPIR-V, each module zstd-compressed in the bundle: 3.5x smaller; `tools/dmsv.py` holds the format) with the translator built from the repository's source (`dm/gfx/tools/dmsh_xlate` over `dm/third_party/ryujinx`, once per player in their nx2android folder), plus the shaders captured on the device (below). Shaders in Oodle-compressed archives (Pokémon Legends) are decoded first, with the game's own decoder: on the device the port already uses, or on the phone itself when the porter runs there | `shader/pkg`, `android/shaders.dmsv`, `android/captured_shaders/` |
| host | `dm/android/build.py --release` with the player's NDK (`--debug`: a development build, debug information and `DM_CTL`) | `android/host/libdmhost.so` (`android/host-debug/`); with `--app`: `libdmplay.so` instead (the host statically linked with the player's JNI entry, the app's `:play` process loads it) |
| apk | The legacy path only (`--game-apk`): `dm/android/apk/mkapk.py`, signed with the player's own key, with the game's gamepad theme only (`dm/android/themes/themes.tsv`: its pack, else the ergo pack) as `assets/overlay/` | `<out>/<App>.apk` — unmaintained in this fork, and it has no launcher page any more (the game is the entry) |
| data | The files the app reads from the pack's own folder | `<out>/<App>-data/{mods,RomFS,aoc,sysdata,shaders.dmsv,nintendo_ext.ttf,env.txt,settings.txt,nx2a-data.json}` (+ `fpslock.tsv` with `--fps60`); the button-icon font is made in `android/font/`; the pack also carries the host (`host/libdmplay.so`), the Vulkan drivers (`drivers/`: the player's own, plus the loader's four hooks — the loader itself is the app's, see below), the gamepad's theme (`overlay/`) and the icon (`icon.png`), all named in the manifest. The manifest (`nx2a-data.json`) names the game, its package, the version, the device features it needs and the profile's own `status` (`playable` / `wip` / `boots` / `experimental`): the app shows an experimental port as such, so a player is told it was never brought up on Android. With `--app` the pack holds no RomFS: `env.txt` points at the build folder's own (`DM_ROMFS=<path>`) and the manifest says the same (`romfs_at`), so the same game is not stored twice on the phone; the app then needs that folder to run the game, and the work folder cannot be cleared on its own |
| install | The legacy path only (`--game-apk`): `adb install`, the profile's `requires` checked against the device, the data pack pushed (optional); the PC tool's `--romfs-at` reads the RomFS from a folder already on the device | |

RomFS in the data pack is hard-linked to the extraction when the volume allows it, so it takes no extra space. On the phone it is not copied at all: the pack points at the build folder's own copy (`DM_ROMFS`), so a game is stored once, not twice.

`--vulkan-driver <lib.so>` packs a Vulkan driver (Mesa's Turnip) in the APK under a `lib*.so` name, beside libadrenotools and its hook libraries, and the data pack's `env.txt` names it (`DM_VK_DRIVER`; `gfx_vk_core.c` loads it through adrenotools, and falls back to the device's driver when it does not load). `python -m porter driver <lib.so> [--package …]` changes the driver of a port already on the device without the game's files (`porter/driver.py`): the installed APK is pulled, written again by `dm/android/apk/apkdriver.py` with the new library in place of the old (every other entry kept, page-aligned and signed again with the player's key by `apksign.py`, the ZIP writer and v2 signer `mkapk.py` uses), installed over the app (its saves stay), and `env.txt`'s `DM_VK_DRIVER` row names it; `--system` drops the library and the row (the device's driver). An APK ported without `--vulkan-driver` has no libadrenotools and is refused: it needs one port with a driver first.

`python -m porter host [--package …]` brings a port on the device to this checkout's host without the game's files (`porter/host.py`): `libdmhost.so` is built again by `dm/android/build.py` from the repository's profile (the title ID from the data pack's `nx2a-data.json`; a debug build for a debuggable app) and put in the installed APK by `apkdriver.py --host`, the driver library kept, with the overlay's font and its license files (`assets/font/`, `pipeline.ui_font_assets`; `--asset` replaces or adds them), which an APK ported before the font came lacks. The game's rewritten modules on the device must fit it: `mods/build_src.sha256` (patch_nso.py) holds the hashes of the rewriter and the patch files that made them, and when any of them differs from this checkout's (the rewriter, `sdk_patches.py`, the game's own `patches.py`, or patches registered for it since) the update is refused and the game needs a port again; other games' patch files are keyed by their own build IDs and do not count, and a changed `sdk_patches.py` does not either when it and the game's `patches.py` still give each of the port's modules (by the build ID in `mods/<module>.cuts.tsv`) the cuts and observation gates its `.cuts.tsv` and `.obs.tsv` list, as after a cut added for another SDK build. The port must also have been made from the repository's profile, since `DM_GAME_MEM_ALIAS` and the rest of `game_profile.h` are compiled into `libdmhost.so`: its version (`nx2a-data.json` `version`) must be one the profile's `build` rows register, and `nx2a-data.json` `profile_h` (the sha256 of the `game_profile.h` the port's host was built with, which `porter port` writes) must equal this checkout's; a derived profile's port (a version the profile does not register, with its automatic alias headroom, issue #26), an `--alias-headroom` port, a profile changed since and a pack from before `profile_h` are refused, and the game needs a port again. The title ID must be 16 hexadecimal digits. Nothing else in the data pack changes (`env.txt`, `shaders.dmsv`): a new shader translator or profile row needs a port again.

## Saves

The app keeps the game's save in its internal storage (`$DM_SAVE`, and `<DM_SAVE>_device` for a game that mounts a device save too: `hle_fs.c`), which a reinstall keeps, an uninstall deletes, and adb cannot read in a release build (it is not debuggable). The save manager (`dm/android/saves_android.c`) copies it in and out through the app's files folder, which adb, porter and the PC reach without a permission:

- `saves/<YYYYMMDD-HHMMSS>/`: one export, the save's files byte for byte, as a console's save tools copy them (so a console's save folder imports as it is, and an export goes back to a console the same way); `saves/<name>.device/` beside it holds the device save.
- **Export save** (the pause menu's Game tab) copies the committed save (never `.work`: a transaction in flight is not a save) on a thread of its own, through a hidden `.part` folder renamed when whole, and starts again if the game commits meanwhile.
- **Import save** opens a picker of the folders in `saves/`, newest first. The import is applied at the next start, before the host mounts anything (`ANativeActivity_onCreate` → `dm_saves_start`), so it never meets a commit: the menu writes `saves/import.txt` and the app ends. At the start the save it replaces is exported first (`<stamp>-before-import`), the folder is copied to `<DM_SAVE>.import` and swapped in with one `renameat2(RENAME_EXCHANGE)`.
- `porter saves` (the GUI's **Saves** tab) does the same from the PC: `apps`, `list`, `export [dest] [--name …]` (a fresh export: the app is stopped and started with `saves/export.txt`, exports and ends without starting the game, then the folder is pulled), `import <folder or .zip>` (pushed under a hidden name, renamed, named in `saves/import.txt`, and the app started to apply it). Each request carries a token the app writes back in `saves/result.txt` with its outcome.
- The files are not changed. A save made on a console belongs to that console's user; a game that keeps its user's id inside its own files (Animal Crossing: New Horizons, issue #16) reads it as another user's, since the host's one user (`hle_account.c`) is not mapped into it.

**The library panel's saves** (`SaveBackup.kt`, `SaveShare.kt`): the panel does not go through the save manager's requests. In the player's mode the host runs inside the app (`dm_java_start` is given the app's own files folder and the title ID), so the live save is the app's own file and the panel works on it directly - an export writes a package, an import applies one, and neither starts the game.

- A package is a zip in `Download/nx2android/`, named `<game>-<titleId>-<stamp>.zip`: the save's files under one folder (the layout the save manager copies out, so a console's save folder is the same thing), with the device save beside it as `<name>.device/` when the game has one. The panel lists the packages and shares one through the system share sheet (a `FileProvider` URI; a `file://` URI is refused since Android 7).
- An import picks a package from anywhere (the built-in file picker), and a package whose name carries another title ID is refused. A package from elsewhere is not trusted: an entry whose path points out of the folder is refused, and the unpacked size is capped.
- The save an import replaces is kept first, as `<stamp>-before-import` in the data pack's `saves/` folder - the name the save manager gives its own backup, so one folder holds every snapshot of the game. The panel lists those backups and can restore, share or delete one.
- The game has to be closed before the save is touched: the host writes it while it runs (the `:play` process's presence is polled).

The save manager keeps its own path for the two callers that cannot work on the save themselves: the host's pause menu and the PC. Its requests (`saves/export.txt`, `saves/import.txt`) and its answers (`saves/result.txt`) are unchanged.

Shaders captured on the device: a game can set shaders whose code is in no game file (Xenoblade Chronicles 3, hundreds: effects and model materials), which the split cannot find. When a draw needs a shader the bundle lacks, the app saves it to `captured_shaders/<key>.bin` in its files folder (`gfx_vk_shader.c` `vk_shader_missing`; the draw is skipped this time). A port with `--install` (the legacy path) first pulls that folder into `<build folder>/android/captured_shaders/`, which is kept from port to port, and `shader_vk.py --capture` translates it into the bundle. These shaders are not in the profile's tables: the tables stay what the game files give. So such a game draws everything only after it has been played that far once and ported again.

The legacy path's install starts the app once before pushing anything: Android makes the app's files folder, owned by the app with the app's group, when the app first asks for it, and a folder the shell makes first lacks that group underneath FUSE, so the app cannot read what is pushed below it. Files whose path passes Windows' 260 characters are pushed through short hard links (adb.exe is not long-path aware). A file already on the device at its size is skipped; the port's own outputs (everything but `RomFS/` and `aoc/`, which change only with the game's version) are also compared by MD5, because a rewriter cut changes a module without changing its size.

What the port refuses: a game whose `main` renders with Vulkan or OpenGL (the Android host replays NVN only so far), and one whose shaders need a step upstream runs by booting the game in the Mac host (GLSLC capture — the shaders a game compiles at run time, which only the Mac host can capture; PlatinumGames' PKZ archives). Game Freak's Oodle archives (Pokémon Legends) and Unreal's shader code archives (Octopath Traveler 0, FINAL FANTASY RESONANCE) are not refused: their decoder runs on the Android device the port already uses, or on the phone itself when the porter runs there (`porter/pipeline.py` `device_oodle`, `local_oodle`).

**Versions.** The newest version in the folder is packed. A version the profile was not brought up on is packed from a derived profile (upstream's `derive_profile`, in `profile-derived/`), without that version's per-build fixes. When another build is packed (GitHub issue #26):
- a profile that declares virtual address memory (a `sys_resource` row, not 0) gets 8 GB more `mem_alias` and `mem_reserve` in its derived copy (`pipeline.alias_headroom`): the address regions such a game reserves depend on its build (Donkey Kong Country Returns HD's base game reached +7.0 GB of alias region, where its tested update stays under +2.75 GB), the tested build's high-water mark does not bind another one, and the heap and the device's memory stay as they are;
- a module whose build has no registered patch, where the tested build of it has some (`dm/tools/sdk_patches.py`, the profile's `patches.py`), gets a `[RED]` line that names the patches it goes without (`pipeline.lost_patches`).

`--alias-headroom <GB>` (0 to 48; the GUI's **Extra address space**, Auto when not given) sets that headroom for any port of such a game: the derived copy, or for a version the profile was brought up on a copy in `profile-mem/` (without `patches.py`, which stays in `dm/games`), which every tool takes first. `0` keeps the profile's layout. It is for a game whose log shows `AllocateAddressRegion … refused (0x1803)` before it crashes; a game without virtual address memory keeps its layout whatever the value.

**Experimental ports** (`--experimental`, the GUI's Experimental box): a game without an Android profile. With no profile at all, upstream's survey (`<game folder>/<title ID>_survey/survey.md`) guesses a provisional one; with only an iOS profile, that profile is copied. Either way it goes to `<title ID>_build/profile/<title ID>/` with an `android.tsv` of status `experimental`, and every tool finds it there (`DM_GAMES_DIR`). That folder is where a bring-up starts; a game that works gets its profile into `nxnative/dm/games/`.

`--package` (the legacy path) installs a port under another package than the profile's, beside the player's other build of the game (a test).

**versionCode** (the legacy path). The APK's versionCode is the packed Switch version number + 1 (v196608 → 196609), so a port of a game update installs over the base game's port. Android installs an APK over one with the same versionCode, but never over a higher one (`INSTALL_FAILED_VERSION_DOWNGRADE`); the only other way past that is an uninstall, which deletes the saves. `--vercode-offset N` (or `NX2A_VERCODE_OFFSET`) adds N, 0 to 65535, so a rebuild of the same version installs over an earlier rebuild with an offset; 65535 at most keeps it below the next version's port, as Switch versions are 65536 apart. A refused downgrade names the installed versionCode.

**Touch games** (`--touch`, the GUI's Touch game box). On Android the game's touch screen takes every touch in both modes, for every game (`hle_hid.c` `touch_on`), but the on-screen gamepad's controls take the touches that go down on them or near them (the app's own hit test, `ui/game/PadModel.kt` `PadHit`, on the geometry the host hands over; about a quarter of a tablet's screen, at its sides), and the gamepad is shown by default. `--touch` writes `overlay=0` into the data pack's `settings.txt` over the profile's settings (`pipeline.TOUCH_SETTINGS`), as Unpacking's profile does: the gamepad starts hidden and every touch is the game's. The app reads that line the first time it sees the game and keeps it as its own preference (`pad.shown.<title ID>`) — the host no longer stores it, so the App's preferences are the only truth about it; the drawer shows the gamepad again. It costs nothing at run time (the host's touch reads are the same with the gamepad shown or hidden). A game that ignores touch while docked needs handheld mode too (the drawer's docked-mode item).

**60 fps** (`--fps60`). A Switch game capped at 30 needs per-build knowledge to run at 60: which memory holds its frame limit, or which code counts frames. A profile that has it (`fps_target`: the rewriter's frame-step stubs or `hle_fpslock.c`'s rows) gets `DM_FPS_TARGET=60` in `env.txt`. Otherwise the port fetches the community's config for the packed `main` build from masagrator's FPSLocker-Warehouse (`porter/fpslocker.py`; GitHub, `SaltySD/plugins/FPSLocker/patches/<title ID>/<build ID>.yaml`) and converts it: the `ALL_FPS` memory writes (pointer chains from `main`, compares; the expressions evaluated for 30 and 60) become `fpslock.tsv` in the data pack, which `hle_fpslock.c` writes on every present (`DM_FPS_LOCKS`); `MASTER_WRITE` bytes become cuts for the rewriter (`patch_nso.py` `DM_PATCHES_EXTRA`, original bytes from the game's `main`); presents follow the display (`DM_PRESENT_INTERVAL=display`), as FPSLocker paces them itself. A config using what the host lacks (`asm_a64`, `DECLARATIONS`, non-`MAIN` regions, `refresh_rate`) is refused whole; 1,160 of the 1,462 configs convert (2026-10-28). A missing, unavailable or refused external config adds no FPSLocker changes; built-in profile patches still apply during the rewrite, independently of `--fps60`. For example, Arceus 1.1.1 already has a build-gated present-interval cut in its `patches.py`. The external-config status does not say whether that device can sustain 60 fps. The warehouse has no license, so its configs are fetched per port and never committed. Whether 60 holds on a device, and whether the config fixes every speed issue, is the config's and the device's: it is the player's choice.

Events: with `--progress json`, every line on stdout is one JSON object, the protocol of upstream's NSP script: `stage`, `step`, `progress`, `stage_end`, `say`; `porter` adds `result` (the outputs) at the end. A line starting `[RED] ` in a `say` is an error or warning.

**Local play over the LAN** (`env DM_LAN=1` in a profile's `android.tsv`; off by default). Local wireless play (`nn::ldn`) runs over the Wi-Fi network the device is on, with the protocol of Atmosphère's ldn_mitm (UDP and TCP port 11452: a station broadcasts a scan, each host answers with its NetworkInfo, a station joins over TCP and the host sends every station the node list), so a port plays with Switches that run ldn_mitm and with other ports on the same network. `hle_ldn.c` answers `nn::ldn` and `nn::nifm` (a local-mode request is granted, an internet request stays refused), `hle_socket.c` puts `nn::socket` on the host's own sockets (Horizon's ABI: FreeBSD's sockaddr, option and flag numbers, Linux's error numbers and `O_NONBLOCK`), and `android/lan_android.c` holds a Wi-Fi multicast lock so broadcasts arrive. Parental controls allow free communication and `nn::friends` makes play history keys locally while it is on. With `DM_LAN` off every one of these stays offline, as before. `DM_LAN_TRACE=1` logs every socket call and every `nn::ldn` / `nn::nifm` query with its result. Online play (Nintendo's servers) stays out of scope.

## What the player installs

The player gets the bundle (`dist/nx2android-<version>-<os>-<cpu>.zip` from `python packaging/build_bundle.py`, for Windows and macOS): unzip, start `nx2android.exe` (`nx2android` on a Mac), nothing to install with pip. It does not ship toolchains; the Setup tab (`nx2android.exe -m porter doctor`, or `python -m porter doctor` from the repository) checks them and the free disk space, and its **Download missing tools** button (`porter tools --download`, `porter/fetch.py`) fetches the missing NDK, .NET SDK and platform-tools from Google's SDK repository and Microsoft's release list, checks each archive against the checksum its list gives, and unpacks them into the player's nx2android folder (`toolchains/`), which the finders search:
- **Android NDK r27c** (`ANDROID_NDK_HOME`, the configured path, or the usual install folders). No Android SDK or JDK: the pack path signs nothing, and the legacy APK path wrote and signed the APK itself (`mkapk.py`).
- **.NET SDK 10**: builds `nx_extract` and the shader translator, and runs them.
- From the repository instead of the bundle: **Python 3.11+** with `requirements.txt` (`lz4`, `capstone`, `pillow`, `fonttools`, and `PySide6` for the GUI): the port runs the engine's own Python tools (the rewriter, the shader split). The bundle carries that Python.
- **adb** (platform-tools), only for the legacy path's install and for the save manager.
- Their own **prod.keys**. Keys and game files are never copied into the repository or the app.

The player's settings, the legacy path's APK signing key and the built translator live in their nx2android folder: `%APPDATA%\nx2android` on Windows, `~/Library/Application Support/nx2android` on a Mac, `~/.config/nx2android` elsewhere (`NX2A_HOME` overrides it). The legacy path's app keeps the same signer across ports, so updates install over it.

## Adding a game

1. `python -m porter port <folder> --experimental`: the survey and a provisional profile. Bring it up from there with the upstream tools and `devtools/` (docs in `nxnative/docs/agents`): the profile moves to `dm/games/<title ID>/`, fixes go into the core as general rules.
2. Add `android.tsv` with `status` and `tested`.
3. `python -m porter port` on its folder: the data pack is the artifact, and the phone app runs the game from it. Raise `status` to `playable` when it is.

## The phone app

`android/` is an Android app (Kotlin, Gradle) that runs the pipeline **on the phone**. It holds no pipeline logic:
it unpacks the environment (the rootfs from the nixport payload, the build tools, the tool's own tree), starts the
porter as a guest program and shows its output. The porter runs with `--app` there: the data pack is the only
artifact, and a finished port runs inside the app — no per-game APK and no installer step. The player lives in
the app's own `:play` process (`com.nx.android.game.GameActivity`): the pack's host (`libdmplay.so`, the host
statically linked with its JNI entry, `dm/android/jni_android.c`) and its driver libraries are copied into the
app's private folder (sdcard is noexec) and loaded there; the surface, input and lifecycle reach the same shared
core the NativeActivity APK serves (`dm/android/jni_android.h`). The game page keeps the volume keys for Android:
the game's audio sits in the media volume group, so the system's volume bar is the game's volume - consuming them
in the app would leave the player with no way to turn the sound up. One game plays at a time; the process ends with
the game, so a crash takes the game down, not the app or a port that is running. The game page is a page of the
app's own task - it sits on top of the library page - so the launcher icon never lands on it, and ending the
game falls back to the library page instead of the home screen. Saves, logs and temp go under
the app's files folder per title id (`DM_GAME_ID`); the game's language and Vulkan driver are picked in the
library's drawer and written into the pack's `env.txt`. The assets are built by `packaging/android-apk/` and are
not committed; the app's own layer rules: no game-specific code, no pipeline logic (the CLI does all of it).

Two things the host does on Android that the desktop host gets from its `main.c`: the **crash handlers**
(`crash_install()`, `dm/host/crash.c`) - without them a SIGSEGV kills the game silently, with no backtrace and no
tombstone - and the **signal alternate stack** of every thread that can fault (`crash_thread_init()`), the guest
threads and the host's own alike. The host's **notices to the app** (the drawer steps aside for a panel) go on a
thread of their own: they are JNI calls into the Activity, and the game's thread must never wait for the app (it
blocked there once, and the game froze with its keyboard never coming up).

### Android source boundaries

| Package | Responsibility |
|---|---|
| `app/` | Root navigation, tab shell and Activity action boundary. `MainActivity` owns Android permissions, intents and system UI. |
| `feature/<name>/` | Routes, Compose screens, ViewModels and UI state. Features call domain contracts rather than own file/network implementations. |
| `domain/` | Platform-independent models, rules and repository/capability contracts. It must not import Android, Compose, `data/` or `feature/`. |
| `data/<name>/` | Repository implementations, platform adapters, persistence and file operations. |
| `core/` | Cross-feature primitives: DI bindings, dispatchers, app paths and shared UI/theme components. |
| `game/{input,hud,overlay}/` | The `:play` process UI grouped by concern. `GameActivity` and `Native` keep their JNI-facing class and method names. |
| `appstate/` | Application-scoped state/coordinators shared across screens and the foreground service; screen presentation state belongs in a feature ViewModel. |

Hilt is the dependency source: application-scoped repositories and state have one binding, Android entry points
inject only the capabilities they use, and Composables receive explicit state/action parameters. The `:play`
process must not start library scans, update checks or port recovery. Long-running work has an explicit owner
(a ViewModel for screen-scoped work, or a service/coordinator for background porting) and a cancellation or recovery path.

`./gradlew :app:check` runs `checkArchitectureBoundaries`: domain cannot import Android, UI, appstate or data;
feature-to-data imports are checked against a file-specific legacy allowlist so new dependencies cannot spread
while the remaining platform integrations are moved behind routes. Remove an allowlist entry as soon as that
call crosses the boundary. The process-shared state in `appstate/` remains application-scoped because the
foreground service, the Activity and multiple feature ViewModels observe the same in-flight work.

### The app's own language

The app's words live in its own resources: `res/values/strings.xml` is English (the default bundle) and
`res/values-zh/strings.xml` is Chinese. The phone picks the bundle — a phone set to Chinese gets the Chinese
one, every other phone the English one — and the player can pick one in the settings (`界面语言` /
**App language**), which takes effect at once and is remembered (`lang` in the app's preferences). The app's
language is not the game's language: the game's own is a per-game setting in the library's drawer, written
into the pack's `env.txt`.

`AppLocale` (`data/AppLocale.kt`) holds the choice and hands out the resources the words are read from. The
screens read them with `stringResource` (the resources are handed to the composition by `core/ui/Locale.kt`), and
the code that has no screen — the state holders, the service, the activity — reads them with
`AppLocale.str()`. Both read the same resources, so a word is the same word wherever it is shown. The data
layer stays free of Android and says what went wrong in a code, not a sentence (`Drivers.Refused`,
`SaveBackup.Refused`); `core/ui/Failures.kt` turns a code into the app's own words.

`tests/test_app_text.py` holds the two tables to each other and the sources to the tables: the same keys on
both sides, no Chinese left in the Kotlin sources, every `R.string` in the table, and every
`stringResource(...)` passing as many arguments as the string has placeholders. It runs in CI, with the rest
of the Python suite.

### The app's own update check

The app on the phone looks for a newer release: once on a cold start (quietly — nothing is said when there is
no network, no release, or nothing newer) and again when the player asks for it in the settings. A newer
release is a notice on the home page and a link to the release page; the app does not download or install
anything itself.

It does not ask the GitHub API for that: an unauthenticated API gives 60 requests per hour per address, and
the phones sit behind the same address more often than not (the driver catalogue stopped using the API for
the same reason). The release page redirects to the newest release's tag, so following that redirect and
reading the last piece of the address is enough.

The three layers, as everywhere else in the app: `domain/UpdateVersion.kt` holds the fork's versions and
their comparison (free of Android, so the tests run on the JVM), `domain/UpdateFeed.kt` reads the
repository's release feed (GitHub's Atom feed: every release with its own notes, already rendered into HTML —
also a plain page, so no API's rate limit), `data/UpdateChecker.kt` asks for the tag and the feed, and
`appstate/UpdateState.kt` holds the state the screens read — the popup on a cold start and the entry in the
settings (`feature/updates/`).

One platform quirk is worth knowing: a locale **with** a region (`en_US`, `zh_CN`) overrides the phone's own
locale, a locale with only a language (`en`) does not — on Android 16 the configuration keeps the phone's
own (`zh_CN`) and the words stay in the phone's language. `AppLocale.locale` therefore gives both languages
a region (`Locale.US`, `Locale.SIMPLIFIED_CHINESE`).

### The Vulkan drivers

A game runs on the device's own Vulkan driver unless the player picks another one in the library's drawer. The
drivers the player picks are **the app's**, not the pack's: they live in the app's own folder, one folder each
(`files/drivers/<id>/`), and the drawer writes the chosen one's **absolute path** into the pack's `env.txt`
(`DM_VK_DRIVER`). The host reads that row (`dm/android/gfx_vk_core.c`), splits it at the last slash and hands the
directory to `libadrenotools`, which loads the library from it in a linker namespace of its own — so a driver may
live anywhere the app can read. One folder per driver because every Turnip build's library is called
`libvulkan_freedreno.so`. The app downloads the drivers (fixed addresses, no release listing: the GitHub API
allows 60 requests an hour per address and a phone shares its address), ships one of them in its assets
(`drivers/Turnip_Gen8_V39.zip`, unpacked into the app's own folder by the app itself when it starts — no network,
no click — and marked as the built-in one, so it is the app's own and not the player's to remove) and imports any
other from the device's files.

In the Android app, `domain/drivers/` owns the driver model and `DriverRepository` contract. `data/drivers/`
owns the app-private directory, archive parsing, fixed download catalogue, import, removal and built-in driver
setup. `feature/drivers/` owns the download route, screen, `DriverViewModel` and its UI state. Hilt binds one
application-scoped repository; Activity and feature entry points inject that same instance. Settings
subscribes to its driver flow for the installed list and sends import/removal actions to the repository. The
library's run options receive that same list from the app root, so all three surfaces observe one source of
installed driver state. New features should keep UI resource selection in `feature/`, storage and network work
in `data/`, and shared models/contracts in `domain/`.

The **loader** (`libadrenotools.so`) is the app's own native library, and it has to be: the host `dlopen`s it **by
name**, and the Android linker looks a bare name up in `LD_LIBRARY_PATH`, in the caller's `DT_RUNPATH` and in the
namespace's default library paths — the app's native library folder is the only one of those the app controls (the
app's private host folder, where the host itself lives, is none of them, so a loader copied there is never found).
Its four hooks travel with the host instead: the host hands the loader the folder it sits in, and the loader looks
the hooks up there.
